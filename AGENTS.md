# HwSync: правила работы агента

Эти правила действуют для всего репозитория, независимо от компьютера и истории чата.

## Начало работы

- Прочитай docs/AI-CONTEXT.md и docs/DECISIONS.md перед изменением кода.
- По задаче прочитай соответствующую инструкцию из docs; карта проектов — docs/CODE-STRUCTURE.md.
- Проверь git status и актуальный код. Документация описывает решения, но не доказывает, что план уже реализован.
- Общайся с пользователем по-русски. При ревью пользователь часто задаёт академические вопросы: объясняй без правок, пока нет явной просьбы изменить код.
- Не коммить и не отправляй изменения без просьбы. Сохраняй чужие незакоммиченные правки.

## Читаемость

- Читаемость важнее микрооптимизаций без измеренного выигрыша; не переписывай код только ради совета анализатора.
- Используй явные типы локальных переменных, интерфейсы для зависимостей и обычные конструкторы.
- Соблюдай .editorconfig, UTF-8 и CRLF во всех редактируемых текстовых файлах.
- Скобки блоков и их содержимое — на отдельных строках; простые автосвойства — на одной строке.
- Отделяй методы и законченные смысловые шаги пустыми строками.
- Перед типами, конструкторами и методами пиши краткий многострочный XML-summary; это относится и к тестам.
- Публичные свойства Entity документируй так же: назначение, единицы измерения, UTC и смысл идентификаторов полезны в подсказках IDE.
- Комментарии внутри методов объясняют неочевидную причину, а не повторяют операторы.
- Для пустых коллекций используй []; сохраняй конструкторы с comparer/capacity и понятные ToList().
- Выбирай if/else или ?: по читаемости; для синхронной блокировки используй System.Threading.Lock.
- Правило параметров и исключения для DI-конструкторов описаны в ADR-002.
- Не возвращай отключённые рекомендации без обсуждения: CA1861 отключена для тестов и отдельно для каталога миграций.

## Архитектура и проверки

- UI должен оставаться тонким; общие службы доступны через интерфейсы и DI. Администратор ПО и участник синхронизации — разные сущности.
- EF Core и сущности базы остаются в Persistence; не передавай их в UI/API-контракты. Решения синхронизации не принадлежат слою БД.
- Миграции остаются отдельной библиотекой и автоматически применяются при старте сервера и клиента — это принятое решение.
- Не меняй стратегию конфликтов, удаления или обработки ссылок под видом рефакторинга.
- Проверяй изменённое поведение подходящими тестами. Тестовые базы и файлы создавай в изолированных временных каталогах; не используй реальные папки пользователя.
- Для сборок агента используй artifacts/client-layers, чтобы не конфликтовать с Visual Studio; логи можно сохранять в artifacts.
- Не удаляй базы, не запускай синхронизацию пользовательских данных и не публикуй секреты без соответствующей явной просьбы.

## Сохранение контекста

- Новое согласованное долгосрочное решение записывай в docs/DECISIONS.md в рамках той же задачи.
- При изменении реализации обновляй профильную инструкцию; AI-CONTEXT.md меняй, если изменились общая картина или точка продолжения.
- Отделяй принятое решение от идеи и реализованного поведения. Не записывай предложение агента как согласие пользователя.
- Не храни в договорённостях токены, личные абсолютные пути, полные логи чата и устаревающие результаты тестов.
