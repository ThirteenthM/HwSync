# Первый этап синхронизации

Направление сервер → клиент. После сравнения кнопка «Копировать отсутствующие» получает только файлы Created. Различающиеся файлы и файлы только на клиенте сохраняются. Передача идёт через HTTP, без обращения клиента к серверному диску.

## Профили папок

Профили хранятся отдельно от синхронизируемых папок в src/HwSync.Client.Windows.Host/sync-profiles.json. Они копируются рядом с exe. В форме профиль выбирается из списка. В начальный профиль перенесены пути текущего appsettings.json.

```json
[
  {
    "Id": "default",
    "Name": "Основная папка",
    "ServerAddress": "http://localhost:5080",
    "ServerRootPath": "E:/HwSync/Server",
    "ClientRootPath": "E:/HwSync/Client001",
    "Rules": {
      "MissingOnClient": "Copy",
      "DifferentFiles": "AskUser",
      "ClientOnlyFiles": "Keep",
      "ServerDeletions": "RecordOnly"
    }
  }
]
```

Id уникален в списке. Эти четыре правила — единственная пока реализованная стратегия. Другие значения отклоняются с сообщением при запуске, а не игнорируются. Изменения формы не сохраняются автоматически. Если файла профилей нет, используется старый appsettings.json как источник одного профиля. Если профили есть, именно они определяют пути и правила.

Для нового профиля добавьте элемент массива. Перезапустите клиент после изменения конфигурации. При смене профиля или путей требуется новое сравнение: результаты от другой папки нельзя применить случайно.

## Копирование

1. Выберите профиль и выполните сравнение.
2. Проверьте список различий.
3. Нажмите «Копировать отсутствующие».
4. После окончания сравните папки повторно.

Файл скачивается во временный файл рядом с назначением. Проверяется размер, выставляется время изменения из снимка сервера, затем файл перемещается на итоговый путь без перезаписи. Если файл уже появился у клиента, он сохраняется. Ошибка или отмена удаляет недокачанный временный файл. Уже скопированные файлы при отмене остаются.

Сервер выдаёт только файлы, входящие в результат конкретного завершённого сравнения, и проверяет их размер и время перед чтением. Если задание вытеснено из памяти или серверный файл изменился, нужно повторное сравнение. Изменения с сохранением размера и времени без хеша пока не обнаруживаются. Ссылки и junction не поддерживаются: сканирование и копирование завершаются ошибкой вместо обхода таких путей. Во время работы не следует менять структуру каталогов извне: полная защита от конкурентной замены путей требует дальнейшей работы с файловыми дескрипторами.

## Серверный учёт удалений

После успешного полного сканирования сервер сохраняет состояние папки. Первое сканирование создаёт исходный снимок: отсутствие клиентского файла на сервере не создаёт удаления. После следующего успешного сканирования исчезнувший серверный файл получает запись:

- RelativePath;
- Deleted = true;
- DeletedAtUtc — время обнаружения удаления, а не точное время операции файловой системы;
- ChangeNumber — возрастающий номер записи удаления в этой папке;
- PreviousFile — последние известные атрибуты.

При повторном появлении файла старые записи помечаются Deleted = false. История не удаляется автоматически. Ошибка сканирования не обновляет историю. Недоступная папка и ошибки доступа не должны превращаться в пустой успешный снимок. Полный успешно прочитанный пустой каталог считается реальным пустым состоянием; определения смены носителя/содержимого точки монтирования пока нет.

Метаданные по умолчанию находятся в LocalApplicationData/HwSync/ServerHistory учётной записи Host, вне синхронизируемой папки. Каждой нормализованной абсолютной папке соответствует отдельный JSON-файл по хешу пути. Запись заменяется атомарно. Параметр Host History:Directory позволяет выбрать постоянное место, например через --set History:Directory=D:/HwSyncMetadata. Для одной папки метаданных поддерживается один процесс Host. При запуске службой учитывайте другую учётную запись и права на хранилище.

GET /api/v1/scan-jobs/{id}/deleted-files возвращает историю удалений папки завершённого задания. GET /api/v1/scan-jobs/{id}/file?relativePath=... отдаёт содержимое файла из результатов сравнения.

Правило RecordOnly означает: клиент пока не удаляет файлы даже при наличии tombstone. Следующий этап — согласование версии клиентского файла и применение подтверждённых удалений с обработкой конфликтов. Номер изменения пока относится только к журналу удалений: курсоры клиента, подтверждения, очистка истории и инкрементальная передача полного набора изменений ещё не реализованы. Полное сравнение всё ещё используется.

## Подготовка двусторонней синхронизации

Добавлен отдельный IReconciliationPlanner / ReconciliationPlanner. Он строит план по трём состояниям: подтверждённому общему состоянию, полному серверному снимку и полному клиентскому снимку. Планировщик не выполняет файловые операции.

В профиле папки появился отдельный раздел Reconciliation:

    "Reconciliation": {
      "ContentConflict": "KeepBoth",
      "DeletionConflict": "AskUser"
    }

Это правила нового планировщика. Действующая кнопка «Копировать отсутствующие» продолжает пользоваться прежними Rules; новый план ещё не подключён к HTTP и форме. KeepBoth пока является результатом планирования, а не реализованным созданием второй копии. Другие стратегии пока не поддерживаются.

FileVersion содержит относительный путь, номер серверной версии и SHA-256 содержимого. ContentHash = null означает явную отметку удаления. Локальные ещё не опубликованные версии могут иметь Revision = 0. Номер версии нельзя подменять текущим ChangeNumber журнала удалений: серверное назначение версий всем изменениям предстоит подключить отдельно. Хеши новый планировщик получает на вход; существующий сканер пока сравнивает размер и время.

Правила:
- Без общего состояния отсутствующий файл считается новым для другой стороны.
- Изменение только на одной стороне передаётся на другую.
- Одинаковое содержимое объединяется независимо от времени изменения.
- Разное изменённое содержимое на обеих сторонах получает KeepBoth.
- Исчезновение ранее подтверждённого файла при неизменной второй копии планирует удаление второй копии.
- Удаление против изменения получает NeedsDecision; автоматической перезаписи или удаления нет.
- Старый файл нового клиента против серверной отметки удаления также требует решения.
- После подтверждённого обеими сторонами удаления повторное создание считается новым изменением.

FolderSyncState связывает подтверждённые версии с ClientId и FolderId. IFolderSyncStateStore / JsonFolderSyncStateStore сохраняет их атомарной заменой JSON; разные клиенты и папки изолированы. Хранилище должен обслуживать один процесс и размещать вне синхронизируемых каталогов. Ошибка чтения не превращается в пустое состояние.

При подключении исполнителя нужно закрепить постоянный ClientId и идентификатор серверной папки, привязать состояние к адресам и путям профиля, вычислять SHA-256 при согласованном чтении, назначать серверные версии и проверять их перед каждой записью. Состояние сохраняется только после подтверждения успешных операций; неразрешённый конфликт сохраняет прежнюю общую версию. При ошибке сканирования нельзя передавать пустой снимок в планировщик. Нужны отдельные операции API для загрузки, условного удаления, подтверждения версий и ручного разрешения конфликтов. Автоматическое распространение удалений в текущем клиенте ещё не включено.

## Ручные действия для отладки

После сравнения доступны четыре независимых действия:
- «Копировать отсутствующие на клиенте (взять на сервере)» — только серверные файлы, без перезаписи.
- «Копировать отсутствующие на сервере (от клиента)» — только клиентские файлы, без перезаписи.
- «Удалить на сервере файлы, которых нет на клиенте».
- «Удалить на клиенте файлы, которых нет на сервере».

Стратегию на этом этапе выбирает пользователь нажатием кнопки. Это ручные операции над последним сравнением; автоматический планировщик конфликтов и распространение удалений между клиентами к ним не подключены. Различающиеся файлы, существующие с обеих сторон, ни одна из кнопок не изменяет.

Перед удалением показывается полный прокручиваемый список, по умолчанию выбрана отмена. Удаление выполняется без корзины. Каталоги не удаляются. Проверяется размер и время удаляемого файла, а также отсутствие второй копии и доступность корневой папки. Файлы, появившиеся после сравнения, не перезаписываются. После любой попытки изменения нужно повторить сравнение; при отмене или ошибке уже выполненные действия остаются. При потере HTTP-ответа результат последнего действия неизвестен — требуется сравнение, автоматического повтора нет.

Проверки соответствуют текущему сканеру (размер и время, без SHA-256). Между проверкой отсутствия на другой стороне и удалением нет распределённой блокировки. Во время отладки не изменяйте папки параллельно: полноценное согласование версий и защита от конкурентных изменений остаются следующим этапом.

Новые маршруты API: PUT /api/v1/scan-jobs/{id}/file?relativePath=... (тело — поток файла), DELETE по тому же адресу и POST /api/v1/scan-jobs/{id}/verify-missing?relativePath=... . Сервер принимает только пути подходящей категории завершённого сравнения. Старое/неподходящее состояние возвращает 409. Размер загрузки ограничен размером файла в снимке; публикация происходит после полной передачи через временный файл. Для использования новых кнопок пересоберите и перезапустите и Host, и клиент.
