# Windows-клиент HwSync

Первый клиент на WPF (.NET 10, Windows). Он обращается к REST API; клиент читает свою папку общим DirectorySnapshotProvider, а сервер читает свою папку самостоятельно.

## Запуск

1. Запустите сервер из корня решения:

```powershell
dotnet run --project src/HwSync.Windows.Server.Host -- --console
```

2. В другом терминале запустите клиент:

```powershell
dotnet run --project src/HwSync.Windows.Client.Host
```

В Visual Studio можно назначить HwSync.Windows.Server.Host и HwSync.Windows.Client.Host несколькими стартовыми проектами. Либо запустить Host отдельно, а клиент выбрать стартовым проектом и нажать F5.

## Работа

- По умолчанию адрес сервера http://localhost:5080. Кнопка «Проверить связь» обращается к /health.
- Укажите два абсолютных пути: папку сервера (источник) и папку клиента (назначение). Клиент читает свою папку в фоне и отправляет только относительные пути, размеры и время изменения. Содержимое файлов и абсолютный путь клиентской папки на сервер не передаются.
- «Сравнить папки» создаёт одно задание и опрашивает его состояние каждые 750 мс. Идентификатор можно скопировать из поля над результатами.
- Таблица показывает тип изменения, относительный путь и размеры файлов в байтах.
- «Отменить» отправляет запрос серверу. Текущий сканер заканчивает чтение каталога, прежде чем подтвердить отмену; это отражается в состоянии.
- При ошибке связи идентификатор и исходное подключение сохраняются в текущем окне. «Продолжить опрос» получает состояние того же задания, не создавая новое.

Направление сравнения — сервер → клиент. «Только на сервере» означает Created, «Только на клиенте» — Deleted, «Отличается» — Modified. Previous в ответе содержит атрибуты клиента, Current — сервера. Одинаковые файлы в результат не входят. Сравнение использует размер и время изменения, не содержимое или хеш. Никакое копирование и удаление не выполняется. Настройки подключения, история и идентификатор текущего задания пока не сохраняются между запусками клиента.

Адрес и каталог заблокированы, пока задание активно, чтобы запрос отмены или опрос не ушёл на другой сервер. При 404 текущее задание снимается с отслеживания: сервер мог перезапуститься или вытеснить историю. Ошибка при отправке запуска не повторяется автоматически — сервер мог принять запрос, даже если ответ потерялся.

Закрытие клиента прекращает локальный опрос, но не отменяет задание на сервере. При активном задании показывается подтверждение закрытия. Чтобы отменить работу, сначала используйте «Отменить».

## Проекты

- HwSync.Api.Client: IHwSyncApiClient и реализация через HttpClient. Зависит только от HwSync.Api.Contracts; поддерживает CancellationToken, строковые перечисления JSON и HTTP-ошибки, включая ProblemDetails. Переданный HttpClient принадлежит вызывающему коду и не уничтожается библиотекой.
- HwSync.Windows.Client.Host: WPF-окна, запуск и контейнер DI. Главное окно принимает IMainViewModel.
- HwSync.Windows.Contract: настройки, перечисления, данные формы и интерфейсы. Без зависимости от WPF и реализаций клиента.
- HwSync.Windows.AppServices: загрузчики конфигурации, MainViewModel, метрики и регистрация реализаций через AddWindowsClientApplication. Контейнер управляет временем жизни модели и HTTP-клиентов.
- HwSync.Client.Tests: проверки стратегии, конфигурации, ViewModel, передачи файлов и DI без окна; net10.0, ссылка только на Application.
- HwSync.Windows.Client.Host.Tests: проверки компоновки окна и его создания через DI; net10.0-windows, WPF и ссылка на Host.
- HwSync.Windows.Server.Host.Tests: интеграционные проверки библиотеки клиента против реального локального HTTP API.

Для отдельного запуска приложению нужен .NET 10 Desktop Runtime. Пример публикации с включённым runtime:

```powershell
dotnet publish src/HwSync.Windows.Client.Host -c Release -r win-x64 --self-contained true -o artifacts/windows-client
```

Адрес допускает HTTP/HTTPS и базовый путь. Проверка TLS-сертификатов не отключается. Сам сервер пока принимает только локальные подключения: полноценный сетевой доступ потребует HTTPS, аутентификации и прав доступа. Клиент не снимает серверное ограничение.

Сканирование не копирует и не изменяет файлы. Результат загружается целиком; строки таблицы виртуализированы, но для очень больших каталогов в будущем нужна постраничная выдача API.

Перед отправкой задания клиент должен успешно прочитать всю свою папку; при ошибке чтения запрос серверу не отправляется. Во время локального чтения кнопка отмены серверного задания ещё недоступна. Повторное сравнение заново читает обе папки.

## Настройки при запуске

Клиент загружает appsettings.json рядом со своим exe (независимо от рабочего каталога). При разработке редактируйте src/HwSync.Windows.Client.Host/appsettings.json: файл копируется при сборке и публикации.

```json
{
  "ServerAddress": "http://localhost:5080",
  "ServerRootPath": "D:\\Data\\Server",
  "ClientRootPath": "D:\\Data\\Client"
}
```

Замените примеры своими путями. В JSON обратный слеш записывается как \\, также можно использовать D:/Data/Client. В репозитории пути оставлены пустыми, чтобы не задавать несуществующие каталоги.

Значения загружаются в поля формы при запуске. Изменения на форме не записываются обратно в конфиг. После редактирования конфигурации перезапустите клиент. Серверный путь относится к компьютеру Host; при чтении конфига существование каталогов не проверяется. Пустые пути разрешены для ручного заполнения, непустые должны быть абсолютными.

Если файла нет, используются адрес http://localhost:5080 и пустые пути. При некорректном JSON или значениях клиент показывает ошибку с путём к конфигурации и завершает запуск.

## Копирование и профили

Добавлено копирование отсутствующих файлов и серверный журнал удалений. Профили и текущие ограничения описаны в [Синхронизация](SYNCHRONIZATION.md).

### Тайм-аут передачи файлов

В appsettings.json клиента параметр FileTransferTimeoutSeconds задаёт максимальное ожидание без прогресса при передаче одного файла в любом направлении. Отсчёт начинается при отправке запроса и продлевается после каждого успешно прочитанного из источника блока загрузки или записанного блока скачивания. Чтение источника означает продвижение HTTP-конвейера, а не подтверждение записи сервером. Ожидание окончательного ответа сервера также ограничено этим интервалом. Общая длительность копирования не ограничена, пока есть прогресс. По умолчанию 1800 секунд (30 минут). Допустимый диапазон: 1–2147483 секунд. Если параметр отсутствует, используется 1800. Для остановки после минуты без прогресса укажите 60. После изменения перезапустите клиент.

Обычные запросы сохраняют тайм-аут 15 секунд. Кнопка «Отменить» прерывает копирование независимо от настроенного времени. Уже скопированные файлы остаются; незавершённый временный файл удаляется при обработке отмены. После отмены или истечения времени повторите сравнение: последний запрос мог успеть выполниться на сервере.

### Метрики копирования

Параметр TransferMetricsEnabled в appsettings.json клиента включает замеры (по умолчанию true). Для отключения укажите false и перезапустите клиент. При отключении таймеры и записи по файлам не создаются, блок метрик скрыт.

После запуска копирования в любом направлении раскройте «Метрики последнего копирования». Для каждой попытки показаны путь, подтверждённый объём, время, средняя скорость и результат. Сводка показывает успешно скопированный объём и среднюю скорость за полное время операции. Объём измеряется в МБ (1 000 000 байт), скорость — в МБ/с: подтверждённые байты / 1 000 000 / время в секундах.

Время включает открытие файла, HTTP-запрос, ожидание ответа и завершение файловой операции. Это эффективная скорость копирования, а не чистая скорость сети. В объём входят только успешно завершённые файлы; пропуски, ошибки и частично переданные файлы при отмене дают нулевой подтверждённый объём. Их время учитывается в общей длительности. При потере ответа загрузка могла завершиться на сервере, но не считается подтверждённой клиентом.

Строки появляются по завершении каждой попытки, итог фиксируется также при ошибке и отмене. Данные хранятся только в памяти до следующей файловой операции или закрытия клиента; на диск журнал метрик не записывается. Замеры не включают предварительное сравнение папок.

## Автосинхронизация по плану

После сравнения колонка «Решение» показывает действие для каждого файла. Наведите курсор на значок для пояснения:

- ↑ — копировать на сервер.
- ↓ — копировать на клиент.
- × ↑ — удалить на сервере.
- × ↓ — удалить на клиенте.
- ? — требуется решение пользователя; файл пропускается.
- — — оставить без изменений по правилу профиля.

Кнопка «Автосинхронизация» выполняет показанный план последовательно. Используются правила выбранного профиля из sync-profiles.json:

- MissingOnClient: Copy — скачать, Delete — удалить серверную копию, Skip или Keep — оставить без изменений.
- ClientOnlyFiles: Copy — отправить на сервер, Delete — удалить клиентскую копию, Skip или Keep — оставить без изменений.
- DifferentFiles: KeepBoth — сохранить обе версии на обоих участниках; AskUser — показать вопрос и отложить решение; Skip или Keep — оставить обе существующие копии на своих местах без запроса решения.
- ServerDeletions / ClientDeletions: Delete — предложить удаление неизменившейся оставшейся копии; AskUser — запросить решение; Skip / Keep / RecordOnly — пропустить. Изменённая либо неизвестная версия всегда требует решения. По умолчанию оба правила — Delete.

По умолчанию MissingOnClient = Copy, ClientOnlyFiles = Keep, DifferentFiles = KeepBoth. Для обмена недостающими файлами в обе стороны установите ClientOnlyFiles = Copy. Для различающихся файлов действует правило профиля или решение, выбранное в строке. В старых профилях замените DifferentFiles = Skip на AskUser, если нужен вопрос в таблице: теперь Skip означает явный пропуск.

Удаление требует подтверждения списка на каждой стороне до начала выполнения плана. История удаления имеет приоритет над MissingOnClient / ClientOnlyFiles. При отсутствии отметки действуют обычные правила односторонних файлов. Проверки актуальности файлов перед действиями сохраняются.

«Отменить» прерывает текущую передачу и дальнейшие действия. При ошибке план останавливается. Уже выполненные операции сохраняются; после запуска требуется повторное сравнение. Смена профиля также сбрасывает план. Просмотр содержимого изображений и сравнение текста будут добавлены отдельно; выбор решения по атрибутам уже доступен.
## Разбор конфликтов

У различающихся файлов есть кнопка «Разобрать». Окно показывает относительный путь, размеры в МБ и даты изменения в UTC. Доступны решения:

- Взять с сервера — заменить клиентскую версию (⇓).
- Взять с клиента — заменить серверную версию (⇑).
- Сохранить обе версии на обоих участниках (⇄).
- Оставить без изменений в этом плане (—).
- Отложить решение (?).

Закрытие окна или «Отмена» сохраняет прежний план. «Добавить в план» обновляет только строку. Реальные действия начинаются по кнопке «Автосинхронизация». Ручные решения действуют до следующего сравнения; конфигурация профиля не переписывается.

KeepBoth сначала сохраняет клиентскую версию под именем вида report (client-conflict-<идентификатор задания>).txt на клиенте и сервере. Только затем клиентский оригинал заменяется серверной версией. Серверный оригинал остаётся под исходным именем. При ошибке дополнительные копии могут уже существовать: они сохраняются, требуется повторное сравнение.

Замена выполняется через временный файл. Проверяются размер полученной версии и размер/дата оригинала перед заменой; ошибка или отмена до замены сохраняет оригинал. Сравнение пока основано на размере и времени: изменения содержимого с сохранением обоих атрибутов не обнаруживаются. SHA-256 и согласование по истории версий — отдельный следующий этап.

История удаления с последними известными атрибутами теперь участвует в построении плана. Если другая копия отличается размером или датой либо прежняя версия неизвестна, показывается вопрос. В диалоге можно восстановить файл из оставшейся копии, подтвердить удаление, оставить без изменений или отложить решение. Само отсутствие файла без истории по-прежнему не считается удалением.

## База SQLite при запуске

Клиент применяет миграции до открытия окна и записывает успешные снимки локальной папки в SQLite. Настройка DatabasePath задаёт абсолютный путь; по умолчанию — %LOCALAPPDATA%/HwSync/Client/state.db. При ошибке базы клиент показывает сообщение и не запускается. Базу нельзя размещать внутри синхронизируемой папки.

Тестовая JSON-история не переносится. Подробности — в SQLITE-STORAGE.md.

## Удаление через Проводник

Сначала выполните успешное сравнение, чтобы обе стороны сохранили исходные снимки. После удаления файла на сервере или клиенте повторите сравнение. Известное удаление определяется до обычного правила Copy: совпадающая по размеру и дате копия получает предложение удаления, изменённая — вопрос.

До публикации плана клиент читает серверную историю через GET deleted-files и свою SQLite-историю. Ошибка чтения блокирует операции; кнопка «Продолжить опрос» повторяет получение истории. Неактивные отметки восстановленных файлов не участвуют в решениях.

Встроенный профиль использует ServerDeletions = Delete и ClientDeletions = Delete. Если в собственном старом профиле сохранён RecordOnly, совпадающая копия будет пропущена, а не удалена и не загружена обратно.

Перед подтверждением удаления доступны «Разобрать» и явное восстановление. Ручные массовые кнопки остаются явным выбором пользователя и не применяют автоматическую стратегию истории.

На текущем этапе идентичность версии определяется размером и датой, без хеша. Удаление файла, которого ещё не было ни в одном успешном снимке, обнаружить невозможно. Подтверждения событий между участниками, обработка смены корневой папки и распределённая блокировка остаются отдельными задачами.
