# SQLite: хранение и миграции

## Проекты

- HwSync.Persistence.Sqlite — подключения и реализации IFolderHistory / IFolderSyncStateStore.
- HwSync.Persistence.Sqlite.Migrations — SQL-миграции, журнал версий и SqliteMigrator.
- HwSync.Persistence.Sqlite.Tests — проверки на независимых файловых базах.

Проект миграций зависит от проекта хранения. Обратной зависимости нет. Контракты остаются в HwSync.Abstractions. Оба проекта — библиотеки net10.0.

## Подключение из Host

SQLite подключён к обоим Host. Существующая тестовая JSON-история не переносится и больше не используется рабочими регистрациями DI. Старые файлы автоматически не удаляются.

Сервер: HostBootstrap регистрирует SqliteDatabase, SqliteMigrator, SqliteFolderHistory и SqliteFolderSyncStateStore. SqliteStartupService вызывает Apply() до запуска ScanWorker и HTTP-сервера. Ошибка миграции прерывает запуск.

Клиент: ClientStorageBootstrap регистрирует SQLite-хранилища. App.OnStartup вызывает Initialize() до создания MainWindow. Проверяются пути профилей и применяются миграции. При ошибке появляется сообщение, окно не открывается, приложение завершается с кодом 1.

После каждого успешного клиентского сканирования HistorySnapshotProvider сохраняет снимок и обнаруженные удаления. На сервере это делает DirectoryChangeScanner. Ошибка чтения не заменяет историю пустым снимком. Первое успешное сканирование новой базы создаёт исходное состояние без отметок удаления.

## Пути к базам

Сервер: Storage:DatabasePath в appsettings.json. Клиент: DatabasePath в appsettings.json. Пустая строка или отсутствие настройки означает:

- сервер: %LOCALAPPDATA%/HwSync/Server/state.db;
- клиент: %LOCALAPPDATA%/HwSync/Client/state.db.

Для собственного пути задайте абсолютное имя файла, например D:/HwSyncMetadata/server.db. Родительский каталог создаётся автоматически. Файл базы должен находиться вне синхронизируемых папок.

Windows Service использует профиль своей учётной записи. Для службы рекомендуется явно задать Storage:DatabasePath в доступном ей каталоге. Для нескольких независимых клиентов на одной машине задавайте разные DatabasePath.

Репозитории сами не обновляют схему. История SQLite уже участвует в выборе действий для известных удалений. Подтверждённые состояния зарегистрированы через DI; полноценное согласование по общим версиям и курсорам ещё не подключено.
## Собственная база участника

Каждый участник получает отдельный файл БД вне синхронизируемых папок. Не копируйте базу как шаблон для другого участника: в ней хранится его постоянный ParticipantId. Файл БД может обслуживать несколько папок.

Начальная схема содержит:

- participant — постоянный идентификатор владельца базы;
- folders — локальный FolderId и нормализованный путь;
- file_snapshots — последнее успешно сохранённое состояние файлов;
- deletion_events — номер события, папка, автор, дата удаления, предыдущие размер и время, признак активности;
- acknowledged_states — подтверждённое состояние пары ClientId / FolderId;
- schema_migrations — применённые версии, имена, контрольные суммы и даты.

Текущий IFolderHistory принимает путь: локальный FolderId назначается при первом снимке и сохраняется в базе. Связь идентификаторов папок разных участников и обнаружение переноса каталога ещё не реализованы.

Номера событий возрастают в пределах базы участника; время не используется как порядок обмена. Первое сканирование создаёт исходное состояние, а не удаления. Повторное сканирование без изменений не повторяет события. Восстановление файла делает прежнюю отметку неактивной, сохраняя историю.

Вызывающий код должен передавать только полностью успешный снимок. Недоступность папки нельзя представлять пустым списком.

Подтверждённые состояния пока сохраняют существующий контракт FolderSyncState в JSON-поле внутри SQLite. Полноценные курсоры доставки, обмен событиями, хеши версий и сборка старых tombstone не подключены. Сам слой БД не принимает решений об удалении файлов.

## Изменение схемы

Начальная миграция: Scripts/0001_initial.sql, встроенный ресурс сборки миграций.

Новые изменения добавляйте отдельными SQL-файлами и включайте в список LoadMigrations() в SqliteMigrator с очередным номером. Применённые миграции не редактируйте. Контрольная сумма выявляет изменения SQL; различие LF / CRLF на неё не влияет.

Ожидающие миграции и записи их журнала применяются в одной транзакции. При ошибке откатываются все изменения этого запуска. Проверяются непрерывность истории, имя и контрольная сумма. Более новая схема либо изменённая миграция запрещают запуск старого приложения.

Используйте транзакционно совместимые SQL-операции. Не включайте в скрипты собственные BEGIN / COMMIT / ROLLBACK и VACUUM. Перед выпуском сложных миграций проверяйте их на копии рабочей БД и предусматривайте резервное копирование.

SQLite включает проверку внешних ключей; время ожидания блокировки — 30 секунд. Изменение снимка и создание событий выполняются одной транзакцией записи.

## Проверка

    dotnet test tests/HwSync.Persistence.Sqlite.Tests/HwSync.Persistence.Sqlite.Tests.csproj

Тесты проверяют повторное применение, обновление существующей схемы, откат, неизменность истории миграций, изоляцию папок и участников, удаление и восстановление файлов, атомарность снимка.
